# Print Models API

Учебен проект по „Уеб сървърно програмиране“, IV курс, специалност
„Софтуерно инженерство“, Пловдивски университет.

REST API за каталог на 3D модели за печат, дизайнери, категории и материали.

## Технологии

- Python 3.12+
- FastAPI и автоматична Swagger документация
- SQLAlchemy 2 за ORM и заявки към SQLite
- Pydantic 2 за API схемите и валидацията (предстои)
- Alembic за миграции
- pytest и HTTPX за тестове
- HTML, CSS и JavaScript за допълнителния frontend (предстои)

## Текущо състояние и етапи

Разработката е разделена на отделни функционални етапи:

1. **Основа:** приложение, база данни, ORM модели, начална миграция и тестове.
2. **CRUD:** отделни Pydantic схеми и операции за създаване, списък,
   извличане по ID, редактиране и изтриване на четирите ресурса.
3. **Бизнес логика:** материали към модели, модели на дизайнер, филтриране,
   преизчисляване на количества и HTTP грешки според заданието.
4. **Втора миграция:** задължително поле `difficulty` със стойности
   `easy`, `medium`, `hard`, съответните ORM и API промени и тест за
   запазване на съществуващите записи при надграждане.
5. **Frontend и завършване:** прост интерфейс към API, проверки на
   desktop/mobile и окончателна документация с примери за всички операции.

В момента е реализиран **етап 1**. CRUD операциите и frontend още не са налични.

## Структура

```text
backend/
    __init__.py
    main.py                # FastAPI приложение
    database.py            # SQLite engine, сесии и dependency
    models.py              # ORM модели и релации
migrations/
    env.py                 # Alembic конфигурация за миграциите
    script.py.mako         # Шаблон за нова миграция
    versions/
        0001_initial.py    # Начални таблици и ограничения
tests/
    test_initial_setup.py  # Тестове на приложението и базата
alembic.ini
requirements.txt
.gitignore
README.md
```

При следващите етапи API схемите ще бъдат в `backend/schemas.py`,
заявките в `backend/crud.py`, а маршрутите в `backend/routes.py`.
Frontend файловете ще бъдат в една папка `frontend/`, без отделен build процес.

## Инсталиране и стартиране под Windows

Командите се изпълняват с PowerShell от основната папка на проекта.
Не е необходимо активиране на виртуалната среда или промяна на execution policy.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
```

- Swagger UI: <http://127.0.0.1:8000/docs>
- OpenAPI спецификация: <http://127.0.0.1:8000/openapi.json>
- Проверка на работещото приложение: <http://127.0.0.1:8000/health>

`GET /health` връща `200 OK` и `{"status": "ok"}`. Проверява работата на
приложението, без да отваря или създава база данни.

## База данни

Локалният файл `print_models.db` се създава в основната папка при изпълнение
на миграциите. Не се добавя в Git. Няма автоматично създаване на таблици
при стартиране на приложението; схемата се управлява само чрез Alembic.
Не се добавят примерни записи при инсталиране.

| Таблица | Полета и предназначение |
| --- | --- |
| `designers` | `id`, `name`, уникален `email` |
| `categories` | `id`, `name`, уникален `name_key` |
| `materials` | `id`, `name`, уникален `name_key` |
| `print_models` | `id`, `name`, `name_key`, `instructions`, `print_time_minutes`, `copies`, `designer_id`, незадължителен `category_id` |
| `print_model_materials` | Съставен първичен ключ (`print_model_id`, `material_id`), `quantity`, `unit` |

Всяка от четирите основни таблици има автоматично генериран целочислен `id`.
`name_key` е помощно поле за сравнение: име без начални/крайни интервали,
обработено с `casefold()`. Така уникалността работи и за имена на кирилица.
Запазва се оригиналният регистър на буквите в `name`.
За един дизайнер комбинацията (`designer_id`, `name_key`) е уникална.
Различни дизайнери могат да имат еднакви имена; имейлите са уникални и
се записват без околни интервали и с малки букви.

Външните ключове са включени за всяка връзка към SQLite чрез
`PRAGMA foreign_keys=ON`. Базата налага следните правила:

- Изтриване на модел: връзките към материалите се изтриват с `CASCADE`;
  материалите се запазват.
- Изтриване на категория: моделите се запазват с `category_id = NULL`.
- Дизайнер с модели и материал, използван от модел, не могат да бъдат изтрити
  поради `RESTRICT`. В API етапа това ще се връща като `409 Conflict`.
- Количеството, времето и броят копия са положителни;
  единиците са само `g`, `m`, `ml`.
- Един материал може да бъде свързан само веднъж с конкретен модел.

Количеството в асоциацията е общото количество за записания `copies`.
Предстоящото преизчисляване ще връща `quantity * requested_copies / copies`
без запис в базата. Лимитът за тази операция е **88 копия**:
`50 + 38`, според факултетен номер `2201322038`. Този лимит се отнася
до заявката за преизчисляване.

## Миграции

```powershell
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic history
.\.venv\Scripts\python.exe -m alembic check
```

Началната миграция е `0001_initial`. Полето `difficulty` ще бъде добавено
с отделна последваща миграция и отделен commit. Началната миграция няма
да се променя за добавянето му. Преди бъдещи промени по база с важни данни
се прави резервно копие на SQLite файла.

## Тестове

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тестовете прилагат миграциите върху временни бази. Те не променят
локалния `print_models.db` и не изискват стартиран сървър.
Проверяват Swagger, началната схема, уникалността на имена и имейли,
ограниченията на количествата и поведението при изтриване.
