# Print Models API

Учебен проект по „Уеб сървърно програмиране“, IV курс, специалност
„Софтуерно инженерство“, Пловдивски университет.

REST API за каталог на 3D модели за печат, дизайнери, категории и материали.

## Технологии

- Python 3.12+
- FastAPI и автоматична Swagger документация
- SQLAlchemy 2 за ORM и заявки към SQLite
- Pydantic 2 за API схемите и валидацията
- Alembic за миграции
- pytest и HTTPX за тестове
- HTML, CSS и JavaScript за допълнителния frontend, без build процес

## Текущо състояние и етапи

Разработката е разделена на отделни функционални етапи:

1. **Основа:** приложение, база данни, ORM модели, начална миграция и тестове.
2. **CRUD:** отделни Pydantic схеми и операции за създаване, списък,
   извличане по ID, редактиране и изтриване на четирите ресурса.
3. **Бизнес логика:** материали към модели, модели на дизайнер, филтриране,
   преизчисляване на количества и HTTP грешки според заданието.
4. **Втора миграция:** задължително поле `difficulty` със стойности
   `easy`, `medium`, `hard`, съответните ORM и API промени и тест за
   запазване на съществуващите записи при надграждане.
5. **Frontend и завършване:** прост интерфейс към API, проверки на
   desktop/mobile и окончателна документация с примери за всички операции.

Реализирани са **етапи 1–5**: REST API, двете миграции и допълнителен
интерфейс за управление на каталога. Интерфейсът използва същия API,
без отделен сървър, Node.js или инсталиране на JavaScript библиотеки.

ORM моделите и API схемите са отделени. Маршрутите използват `Depends(get_db)`
за сесия към базата и извикват функциите от `crud.py`.
Frontend файловете са в една папка `frontend/`. FastAPI сервира началната
страница на `/`, а CSS и JavaScript — под `/static`.

## Инсталиране и стартиране под Windows

Командите се изпълняват с PowerShell от основната папка на проекта.
Не е необходимо активиране на виртуалната среда или промяна на execution policy.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m alembic upgrade head
.\.venv\Scripts\python.exe -m uvicorn backend.main:app --reload
```

Ако виртуалната среда и зависимостите вече са инсталирани, за следващо
стартиране са достатъчни последните две команди. `alembic upgrade head`
запазва съществуващите данни и прилага само липсващите миграции.
Спирането на сървъра става с `Ctrl+C` в терминала.

Отвори **http://127.0.0.1:8000/** за интерфейса или
**http://127.0.0.1:8000/docs** за Swagger. Не отваряй `index.html`
директно от диска — заявките към API изискват стартирания сървър.

## Работа през интерфейса

1. В „Дизайнери“ добави име и валиден имейл. Може да редактираш или
   изтриеш запис; „Виж модели“ показва моделите на конкретния дизайнер.
2. По желание създай категории, а в „Материали“ добави нужните
   наименования, например PLA. Не се зареждат автоматично примерни данни.
3. В „Модели“ избери „Добави модел“. Попълни име, дизайнер, трудност,
   копия, време в минути и инструкции. Категорията е незадължителна.
4. Използвай „Търси“ за едновременно филтриране по име, категория и
   максимално време. „Изчисти“ възстановява целия каталог.
5. „Детайли“ показва инструкциите и материалите. Избери съществуващ
   материал, въведи положително количество и единица `g`, `m` или `ml`.
   Количеството е общо за записания брой копия. Връзката може да се
   редактира или премахне, без да се изтрива материалът от каталога.
6. В същия прозорец въведи от 1 до 88 копия и натисни „Преизчисли“.
   Резултатът се показва, без да променя запазените количества и копия.

Изтриването изисква потвърждение. Дизайнер с модели и използван материал
не могат да се изтрият; съобщението от API се показва в интерфейса.
Изтриването на категория запазва моделите без категория. Изтриването
на модел запазва материалите и премахва само неговите връзки към тях.
За затваряне на прозорец използвай бутона „Затвори“ или `Esc`.

- Swagger UI: <http://127.0.0.1:8000/docs>
- OpenAPI спецификация: <http://127.0.0.1:8000/openapi.json>
- Проверка на работещото приложение: <http://127.0.0.1:8000/health>

`GET /health` връща `200 OK` и `{"status": "ok"}`. Проверява работата на
приложението, без да отваря или създава база данни.

## CRUD операции

| Ресурс | Списък и създаване | Конкретен запис |
| --- | --- | --- |
| Дизайнери | `/designers` | `/designers/{designer_id}` |
| Категории | `/categories` | `/categories/{category_id}` |
| Материали | `/materials` | `/materials/{material_id}` |
| Модели за печат | `/print-models` | `/print-models/{print_model_id}` |

Всеки ресурс поддържа:

| Метод | Операция | Успешен статус |
| --- | --- | --- |
| `GET` на списък | Всички записи, подредени по `id`; празен списък при липса на записи | `200 OK` |
| `POST` на списък | Създаване и връщане на запис с генериран `id` | `201 Created` |
| `GET` на конкретен запис | Извличане по `id` | `200 OK` |
| `PUT` на конкретен запис | Редакция с всички задължителни полета | `200 OK` |
| `DELETE` на конкретен запис | Изтриване | `204 No Content`, без тяло |

`PUT` използва същото JSON тяло като `POST`, без `id`. Това е пълна
редакция, а не частична. За модел пропуснат или зададен като `null`
`category_id` премахва категорията. Помощното поле `name_key` не присъства
в API отговорите и не се приема във входните данни.

### Примери за тестване през Swagger

В `/docs` избери операция, натисни **Try it out**, въведи JSON тялото и
натисни **Execute**. Следните данни са само примери за ръчно тестване.

1. Създай дизайнер чрез `POST /designers`:

   ```json
   {"name": "Иван", "email": "ivan@example.com"}
   ```

2. По желание създай категория чрез `POST /categories`:

   ```json
   {"name": "Играчки"}
   ```

3. Създай материал чрез `POST /materials`:

   ```json
   {"name": "PLA"}
   ```

4. Създай модел чрез `POST /print-models`. Замени примерните ID стойности
   с върнатите от предходните заявки; без категория използвай `null`:

   ```json
   {
     "name": "Куб",
     "instructions": "Печат със слой 0.2 mm и запълване 20%.",
     "difficulty": "easy",
     "print_time_minutes": 30,
     "copies": 2,
     "designer_id": 1,
     "category_id": 1
   }
   ```

5. Провери модела с `GET`, редактирай го с `PUT`, после го изтрий с `DELETE`.
   За `PUT` подай цялото тяло от примера с желаните промени.
   Докато дизайнерът има модел, изтриването на дизайнера връща `409`.

### Валидация и грешки

- Имената и инструкциите са задължителни и се изчистват от начални/крайни
  интервали. Празни и съставени само от интервали стойности се отхвърлят.
- Имейлът трябва да е валиден; околните интервали се премахват и буквите
  се преобразуват до малки.
- `print_time_minutes`, `copies` и свързаните ID стойности са положителни
  цели JSON числа в диапазона на SQLite: от `1` до `2^63 - 1` включително.
  Низове, дробни числа и булеви стойности не се приемат.
  ID стойностите в пътищата са в същия числов диапазон.
- `category_id` е незадължителен. `designer_id` е задължителен.
- `difficulty` е задължителен при създаване и редакция на модел;
  допустимите стойности са точно `easy`, `medium` и `hard`.
- Непознати полета, включително подаден от клиента `id`, се отхвърлят.

| Статус | Причина |
| --- | --- |
| `404 Not Found` | Несъществуващ запис или несъществуващ дизайнер/категория при запис на модел |
| `409 Conflict` | Дублиран имейл, дублирано име на категория/материал, дублирано име на модел за същия дизайнер или забранено изтриване |
| `422 Unprocessable Content` | Невалидно тяло, липсващи задължителни полета, невалиден ID или query параметър |

Грешките съдържат поле `detail`. При конфликт транзакцията се отменя;
неуспешната редакция не променя съществуващия запис. В отговорите
не се връщат SQL заявки или вътрешни съобщения от базата.
Грешките от валидацията съдържат `type`, `loc` и `msg`, без копие на
подадената стойност. Това позволява валиден JSON отговор и за невалидни
числа като `NaN`, без те да се отразяват обратно в отговора.

## Свързани записи и материали на модел

| Метод и път | Предназначение | Успешен статус |
| --- | --- | --- |
| `GET /designers/{designer_id}/print-models` | Всички модели на конкретен дизайнер | `200` |
| `GET /print-models/{print_model_id}/materials` | Материалите на модела с количества и единици | `200` |
| `POST /print-models/{print_model_id}/materials` | Добавяне на съществуващ материал | `201` |
| `PUT /print-models/{print_model_id}/materials/{material_id}` | Редакция на количеството и единицата | `200` |
| `DELETE /print-models/{print_model_id}/materials/{material_id}` | Премахване само на връзката | `204`, без тяло |

За списъците несъществуващ дизайнер/модел връща `404`. Съществуващ
основен ресурс без свързани записи връща `200` и `[]`.

Примерно тяло за добавяне на материал, създаден предварително през
`POST /materials` (замени `material_id` с действителния върнат ID):

```json
{"material_id": 1, "quantity": 40, "unit": "g"}
```

Количеството е общо за записания брой копия на модела. То трябва да бъде
положително крайно JSON число; единицата е точно `g`, `m` или `ml`.
За редакция подай само количеството и единицата:

```json
{"quantity": 50.5, "unit": "g"}
```

Отговорът за връзка включва и информация за материала:

```json
{
  "quantity": 50.5,
  "unit": "g",
  "material_id": 1,
  "material": {"name": "PLA", "id": 1}
}
```

Повторно добавяне на същия материал към същия модел връща `409`, без
промяна на запазеното количество. Един материал може да участва в различни
модели с различни количества и единици. Несъществуващ материал/модел или
липсваща връзка при редакция/премахване водят до `404`.
Премахването на връзката запазва материала.

## Филтриране на модели

`GET /print-models` приема незадължителни query параметри:

| Параметър | Значение |
| --- | --- |
| `name` | Част от наименованието, без значение на регистъра и околните интервали, включително за кирилица |
| `category_id` | ID на категорията |
| `max_print_time` | Максимално време в минути, включително подадената стойност |

Пример: `/print-models?name=куб&category_id=1&max_print_time=30`.
Всички подадени филтри се изпълняват едновременно с логика **AND** чрез
SQL заявка. Без филтри се връщат всички модели. Празно име или име само
от интервали не ограничава резултатите. Символите `%` и `_` в търсенето
се разглеждат като обикновени символи.

Числовите филтри са положителни цели числа в диапазона на SQLite.
При липса на съвпадения, включително за несъществуващ `category_id`,
се връща `200` и `[]`. Невалиден филтър връща `422`.

## Преизчисляване на количества

`GET /print-models/{print_model_id}/scaled?copies=8` връща модела с
материалите и количествата за желания брой копия. `copies` е задължителен
query параметър от **1 до 88** включително. При стойност извън този
диапазон или невалиден параметър се връща `422`; за липсващ модел — `404`.

Формулата е `quantity * (requested_copies / stored_copies)`.
Ако са записани 40 g за 4 копия, заявка за 8 копия връща 80 g.
В отговора `copies` е желаният брой; добавя се списък `materials`
със същата структура като при извличане на материалите на модел.
Без материали списъкът е празен. Останалите полета на модела се запазват.

Операцията не променя базата: следващото обикновено извличане връща
първоначалните копия и количества. Ако изчисленото количество е извън
поддържания числов диапазон, също се връща `422`.

## База данни

Локалният файл `print_models.db` се създава в основната папка при изпълнение
на миграциите. Не се добавя в Git. Няма автоматично създаване на таблици
при стартиране на приложението; схемата се управлява само чрез Alembic.
Не се добавят примерни записи при инсталиране.

| Таблица | Полета и предназначение |
| --- | --- |
| `designers` | `id`, `name`, уникален `email` |
| `categories` | `id`, `name`, уникален `name_key` |
| `materials` | `id`, `name`, уникален `name_key` |
| `print_models` | `id`, `name`, `name_key`, `instructions`, `difficulty`, `print_time_minutes`, `copies`, `designer_id`, незадължителен `category_id` |
| `print_model_materials` | Съставен първичен ключ (`print_model_id`, `material_id`), `quantity`, `unit` |

Всяка от четирите основни таблици има автоматично генериран целочислен `id`.
`name_key` е помощно поле за сравнение: име без начални/крайни интервали,
обработено с `casefold()`. Така уникалността работи и за имена на кирилица.
Запазва се оригиналният регистър на буквите в `name`.
За един дизайнер комбинацията (`designer_id`, `name_key`) е уникална.
Различни дизайнери могат да имат еднакви имена; имейлите са уникални и
се записват без околни интервали и с малки букви.

Външните ключове са включени за всяка връзка към SQLite чрез
`PRAGMA foreign_keys=ON`. Базата налага следните правила:

- Изтриване на модел: връзките към материалите се изтриват с `CASCADE`;
  материалите се запазват.
- Изтриване на категория: моделите се запазват с `category_id = NULL`.
- Дизайнер с модели и материал, използван от модел, не могат да бъдат изтрити
  поради `RESTRICT`. API връща `409 Conflict`.
- Количеството, времето и броят копия са положителни;
  единиците са само `g`, `m`, `ml`.
- Един материал може да бъде свързан само веднъж с конкретен модел.

Количеството в асоциацията е общото количество за записания `copies`.
Преизчисляването връща `quantity * (requested_copies / copies)`
без запис в базата. Лимитът за тази операция е **88 копия**:
`50 + 38`, според факултетен номер `2201322038`. Този лимит се отнася
до заявката за преизчисляване.

## Миграции

```powershell
.\.venv\Scripts\python.exe -m alembic current
.\.venv\Scripts\python.exe -m alembic history
.\.venv\Scripts\python.exe -m alembic check
```

Историята съдържа две последователни миграции:

1. `0001_initial` създава основните таблици и ограничения.
2. `0002_add_difficulty` добавя `difficulty` с `NOT NULL` и `CHECK` за
   стойностите `easy`, `medium`, `hard`. Началната миграция е непроменена.

Втората миграция използва директно `ADD COLUMN`, без пресъздаване на
таблицата. Съществуващите модели получават `easy`; всички техни данни и
връзки с материали се запазват. В базата остава стойност по подразбиране
`easy`, необходима за безопасното добавяне на задължителната колона.
API изисква изричен `difficulty` при всеки `POST` и `PUT` на модел.

`alembic upgrade head` прилага и двете миграции при нова инсталация или
само втората при база на `0001_initial`. Повторното изпълнение не променя
вече актуална база. След надграждане `alembic current` трябва да показва
`0002_add_difficulty (head)`, а `alembic check` да не отчита разлики.

Преди промени по база с важни данни се прави резервно копие на SQLite
файла. Тестът за обратна миграция работи само с временна тестова база.

## Тестове

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

Тестовете прилагат миграциите върху временни бази. Те не променят
локалния `print_models.db` и не изискват стартиран сървър.
Проверяват Swagger, началната схема, уникалността на имена и имейли,
ограниченията на количествата и поведението при изтриване. API тестовете
покриват пълен CRUD цикъл за всеки ресурс, валидация при създаване и
редакция, липсващи ресурси, конфликти и запазване на данните след грешка.
Допълнително проверяват управление на материалите на модел, празни
списъци и липсващи родители, комбинирани филтри, преизчисляване до 88
копия и запазване на първоначалните данни след преизчисляване.
Тестовете за `difficulty` проверяват трите валидни стойности, задължителното
поле, отказа на невалидни стойности в API и в базата, както и надграждане
от първата миграция с вече съществуващи записи и материални връзки.
